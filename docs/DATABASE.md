# Database design

Use PostgreSQL, SQLAlchemy 2, and Alembic migrations. Keep model, migration, API schemas, and tests consistent.

## Tables
### `users`
UUID, normalized unique email, display name, password hash or identity-provider subject, role (`admin|staff|viewer`), active flag, created/updated timestamps. Never store plaintext passwords.

### `labs`
UUID, name, optional location, active flag, created/updated timestamps.

### `devices`
UUID, lab FK, hostname, optional display name, platform, agent version, active flag, nullable `last_seen_at`, timestamps. Avoid unnecessary hardware serial collection.

### `agent_credentials`
UUID, device FK, token hash, created/expiry/revocation/last-used timestamps. Never store or log raw token.

### `metrics`
ID, device FK, server `recorded_at`, optional agent timestamp, CPU percent, memory percent, optional memory used/total bytes, disk percent and used/total bytes. Percentages 0–100; byte counts non-negative. Index `(device_id, recorded_at DESC)`.

For multiple volumes, prefer a child metric-volume table (`metric_volumes`) with volume label, percent, used bytes, total bytes, rather than assuming one `C:` drive.

### `alerts`
UUID, device FK, type (`heartbeat_missing|cpu_high|memory_high|disk_high`), severity, status (`open|acknowledged|resolved`), dedupe key, title/message, first/last-seen and lifecycle timestamps. Enforce deduplication of active alerts.

### `incidents`
UUID, optional device FK, title, description, priority, status (`open|acknowledged|in_progress|resolved|closed`), creator/assignee FKs, resolution note, timestamps. Index status and creation time.

### `audit_logs`
ID, actor user (nullable for system), action, entity type/id, allow-listed JSON metadata, timestamp. Never store secrets or raw tokens in metadata.

## Constraints
Foreign keys; unique normalized email; unique device identity policy; check constraints for percentages and byte counts; server-side credential/device binding; transactions for heartbeat, enrollment, alert and audited changes. Prefer deactivation over destructive deletion where history exists.

## Retention
Proposed starting policy: raw metrics retained 30 days, subject to college approval. Do not enable destructive cleanup until the policy is confirmed and the job is tested. Incident/audit retention is separate.

## Migrations
Every schema change requires Alembic migration. Review autogenerated migrations. Test upgrade from an empty DB and, where feasible, from the prior migration. Never edit an already-applied production migration.
